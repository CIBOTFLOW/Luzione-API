Outcome: preserve the frozen `TenantBlueprint/v1`, `SetupMandate/v1`, `ImportBatch/v1` and `ImportReceipt/v1` business documents while publishing a strict successor transport/mapping boundary that binds source schema bytes and exact L2 mapper/evidence provenance, requires a separately verified human subject for approval/revocation, derives mandate activity only from append-only events and prevents caller-selected import outcomes.

Entrypoints remain the existing tenant-scoped onboarding routes, with one additive POST `/api/v1/onboarding/setup-mandates/revocations`. The UI workload remains the transport caller. Approval and revocation additionally require a signed, non-anonymous Supabase user JWT whose issuer/signature/lifetime/session subject, tenant and capability are verified independently; a service token configured with `actorType=user` is never human evidence. Authorization claims are read only from signed `app_metadata`, never user-editable metadata.

Authoritative truth remains P110 plus tenant-scoped Postgres. Blueprint identity/reservation includes authenticated tenant, source pack ID/version, source content digest, exact admitted Tenant Pack schema digest, mapping version and the canonical digest of the L2 implementation/mapper/evidence binding. L2 bindings are exact, server-admitted configuration records and default to none. L2 may not select canonical identity, approval, revocation, limits, receipt or finality.

Contract evolution is additive and explicit: existing `LuzioneOnboardCoreApi/v1`, `TenantBlueprintMap/v1`, `CRMImportDryRunMap/v1` and `ConnectorSyncValidation/v1` remain historical pins. Corrected requests use `LuzioneOnboardCoreApi/v2`, `TenantBlueprintMap/v2`, `TenantPackSourceBinding/v1`, `LuzioneHumanApprovalSubject/v1`, `SetupMandateRevocation/v1`, `CRMImportDryRunMap/v2`, `ConnectorSyncValidation/v2` and `ConnectorValidationOutcome/v1`. Frozen Core contract bytes and semantics do not change.

Import rows carry only immutable source-row, match-key and payload digests. L1 groups the exact row manifest and derives `ACCEPTED`, `DUPLICATE`, `CONFLICT` or `REJECTED`; caller-declared outcome/reason fields are rejected. The import requires the exact binding digest inherited by its Mandate. Runtime starts at the API-owned job boundary, sets a transaction-local timeout, measures elapsed time, persists the measurement with the receipt and atomically rejects/rolls back an overrun. `maxRuntimeMinutes` therefore remains effective authority rather than decorative metadata.

Connector validation is also a v2 boundary. It pins the exact same-tenant Mandate and binding digest and accepts only an active, unexpired, unrevoked Mandate with an unsuperseded human approval and `VALIDATE_CONNECTOR_READBACK`. Its server-owned deadline applies across reservation, sandbox dispatch and readback. `SyncReceipt/v1` remains frozen: `SOURCE_CONFIRMED` requires matching readback, `RECONCILING` is pending only and `ACKNOWLEDGED` is pre-reconciliation only. A separate strict `ConnectorValidationOutcome/v1` carries typed non-success for `BLOCKED`, `VERSION_MISMATCH`, `AMBIGUITY_EXHAUSTED` and `TERMINAL_UNAVAILABLE`; those states never expose a success receipt.

No production database, credential, provider, scheduler, customer effect, default branch, merge, deployment promotion or live rollback is in scope.
